## What 1.2.1 actually delivers

A new `morphic-ingest::json` module: `parse_json` / `parse_json_with`, sharing `IngestOptions`,
`CancelToken`, `Progress` and `ImportReport` with the CSV path.

**Scope decision — this is the parser, not a user-visible feature.** `morphic-core` and the
bridge still call CSV only, and the import screen still says *"JSON and structured logs are
not supported yet."* Auto-detection and the `formatHint` UI are task 1.2.3, and the import UX
is 1.2.4. Wiring JSON into the app before sniffing exists would mean a second hard-coded
entry point to rip out again. **Nothing a user can see changes in 1.2.1**, and this document
does not claim otherwise.

### Shapes

| Input | Result |
|---|---|
| `[{…}, {…}]` | one row per element |
| `{…}` | one row |
| `[1, 2, 3]` | a single `value` column, reported |
| top-level scalar | one row, `value` column |
| element that is itself an array | quarantined, not guessed at |
| `{"data":[…],"meta":{…}}` | one row + a warning naming the record-array fields |

The wrapper case is deliberate: silently picking one of several arrays would be wrong often
enough to be harmful. Extracting a wrapper belongs to 1.2.4's re-import-with-hint flow.

### Bounded memory

The document is **not** materialised as a `serde_json::Value` tree when the top level is an
array — that costs roughly 5–10× the file size and would defeat the 256 MiB gate on a 4 GB
phone. A forward-only scanner tracks string state, escapes and nesting depth, and yields one
element slice at a time, so peak parse memory is the largest *element*, not the file.

Two new gates, both returning the new `IngestError::ResourceLimit` with actionable copy:

- `max_import_bytes` — **256 MiB**, checked before any parsing work.
- `max_memory_bytes` — **512 MiB**, checked per row against retained cell bytes.

`max_rows` / `max_columns` are reused; the column cap applies to the **union** of keys across
all records, not to any single record.

### Flattening

Dotted paths to **depth 4**. Nothing is dropped: a subtree deeper than the cap, and any array
value, is retained as **compact JSON text** in that column, with one warning per affected
column (not per row). `{}` and `[]` are kept so a field's existence survives. Keys that
collide after flattening (`{"a.b":1}` vs `{"a":{"b":2}}`) get a numeric suffix and a warning.

### Typing and nulls

Scalars are rendered to text and passed through the **same** `column::build_column` ladder as
CSV, so the formats cannot drift apart on types and ISO-8601 strings from APIs become real
timestamps.

Nulls come from JSON `null` or an absent key **only**. The CSV null-token vocabulary is
deliberately not applied — `"null"`, `"N/A"` and `""` are real string data in JSON, and
applying CSV's vocabulary would silently destroy them. Absent keys are back-filled as null in
both directions as the column union grows.

### Robustness

- A malformed element does not discard the rows already read; it is quarantined and counted.
- More than `max(1% of rows, 1000)` unreadable elements fails the import with diagnostics
  (architecture/05 §1.3) rather than importing nonsense.
- A trailing comma is accepted **and reported**; content after the closing `]` is ignored
  **and reported**. A leading/doubled comma or an unclosed array is a typed error.
- Cancellation and the `Sniffing → Parsing → Typing → Done` progress contract match CSV.

## What 1.2.2 actually delivers

Three new parsers — `jsonl`, `text`, `log` — plus a `records` module extracted from the JSON
parser so the JSON-shaped formats share one flattening/null/naming/typing/quarantine policy
instead of two copies that drift. A test asserts JSON and JSONL produce identical columns,
types and null masks for identical records.

**Still parser-only.** Core and the bridge continue to call CSV; auto-detection is 1.2.3.
Nothing a user can see changes in 1.2.2 either.

### JSONL

Streaming line-at-a-time. Blank lines skipped, trailing newline is not a row, CRLF handled.
A bad line is quarantined without ending the parse and the **first 20 line numbers** are
reported (architecture/05 §1.3).

### TXT

`line_number` + verbatim `line`. **Blank lines are kept** and reported — dropping them would
misalign every line number against the source. Text is never trimmed. Both columns still go
through the shared type ladder.

### LOG — pattern library v1

`regex` was already locked and is the crate dependency-strategy §3 names for this job, so no
new supply-chain surface. Patterns are compiled once via `OnceLock`.

The pattern is chosen **once** from up to 256 sampled lines, then applied to every line — a
file cannot end up half-parsed one way and half another. Selection evidence (pattern, match
count, rate) is always reported; below the documented 70% bar a low-confidence warning is
added.

| Pattern | Core columns |
|---|---|
| `iso-level` | time, level, service, message |
| `syslog` | time, level, host, service, pid, message |
| `common-log` | time, host, ident, authuser, message, status, bytes, referer, user_agent |
| `logfmt` | time, level, service, message (from aliases) |
| `fallback` | time, level, message |

Core columns are always emitted (null when absent) so column order never depends on which
line carried a field first. `key=value` pairs are promoted to columns, capped at **64**
distinct keys with the cap reported; a tail key can never overwrite a field the structured
prefix already extracted. Levels canonicalise for grouping, syslog `PRI` decodes to a
severity, and CLF `-` becomes null. **Unmatched lines keep their entire raw text in
`message`** — a log import never fails and never drops a line for looking odd.

## Limitations and debt introduced or found by 1.2.1

- **JSON column order within a record is sorted, not file order.** `serde_json`'s default
  `Map` is a `BTreeMap`, so `{"date":…,"open":…,"close":…}` yields `close, date, open`. It is
  deterministic and pinned by a test, but it is not what the file said. Preserving source
  order needs a local order-tracking deserializer (1.2.4): enabling
  `serde_json/preserve_order` workspace-wide would reorder every serialized document and
  break the schema and compiler goldens.
- **CSV and JSON now differ on the quarantine ceiling.** JSON enforces `max(1%, 1000)`; CSV
  still only warns and stops after 100 consecutive failures. Aligning them is 1.2.3 work.
  Recorded here rather than left as a silent behavioural difference between formats.
- Array elements that are themselves arrays are quarantined rather than flattened into
  positional columns. No corpus evidence yet says that is the right call; revisit in 1.2.4.
- A single top-level object is still parsed whole. The byte gate bounds it, but a 200 MiB
  single object will spike memory in a way a 200 MiB array will not.
- Ingestion remains whole-file in memory for the decode step (inherited M1.1 debt); the JSON
  scanner removes the *parse-tree* multiplier, not the decoded `String`.
- `chardetng` statistical charset detection is still outstanding (1.2.3).

## Limitations and debt introduced by 1.2.2

- **Log service detection is a heuristic.** `[svc]` is unambiguous; a bare token is taken as
  a service only when it starts lowercase. `INFO Request received` keeps the phrase as the
  message, but `INFO request received` reads `request` as a service. Disclosed on every
  iso-level import rather than hidden.
- **syslog and CLF timestamps stay text.** RFC3164 has no year; CLF uses month names. The
  temporal ladder refuses both rather than guessing, and a warning says so. Promoting them
  depends on the locale/year inference M1.1 deliberately deferred.
- The pattern library is **v1**: no multiline/stack-trace folding, no JSON-in-log detection,
  no Apache error-log or klog pattern. These are extraction gaps, not data loss — unmatched
  lines survive verbatim.
- TXT and log parsing still decode the whole file to a `String` first (inherited M1.1 debt).
  The per-line parse is streaming; the decode is not.
