## 1. Task 1.4.1 — scene contracts and the aggregation behind them

`docs/architecture/02` §2.5 promises that `chartData` is pre-aggregated in Rust and that charts
never receive raw tables. This task is that promise, end to end: three scene shapes, their
ceilings, the aggregation paths that fill them, and a Dart contract that carries the result
without recomputing it.

| Layer | Where |
|---|---|
| Scene types, ceilings, aggregation | `engine/crates/morphic-query/src/chart.rs` |
| `Engine::chart_data` + scene cache | `engine/crates/morphic-core/src/lib.rs` |
| Binding-filter composition for charts | `engine/crates/morphic-core/src/plans.rs` |
| `morphic_chart_data`, API version 6 | `apps/morphic_flutter/rust/src/lib.rs` |
| Sealed Dart scene contract | `lib/engine/chart_scene.dart` |
| Bridge + controller read path | `lib/engine/bridge.dart`, `engine_controller.dart` |
| Aggregation bench | `engine/crates/morphic-query/tests/perf.rs` |

**Painters are deliberately not here.** 1.4.2–1.4.4 own them. What ships now is the contract
they will consume, so three painters can be built against a fixed shape instead of each
inventing one.

## 2. Decisions worth recording

**`Other` is re-aggregated, never subtracted.** For count and sum the remainder could be grand
total minus the top N. But an average of averages is not an average, and min/max/distinct do not
subtract at all. So the remainder always comes from aggregating the rows that missed the cut —
one extra pass buys an answer correct for every operator. A Dart test pins it with a fixture
chosen so the two answers differ: the remainder's true average is 15, where averaging the group
averages gives 12.5. The first draft of that test used values where both were 20 and proved
nothing.

**The null *category* sorts last, not its measure.** A null region with a large average is still
an absent category; floating it to the top would contradict the nulls-last policy the table
already promises. This was a bug in the first draft of the comparator.

**The point ceiling is total across series.** Eight series of 2000 points is 16000 points to
paint, which is the cost the ceiling exists to bound. The axis is bucketed to fit the ceiling
divided by the series kept.

**Top-N sees every category.** `group::execute` clamps intermediate groups to `MAX_GROUPS`
(2000) because its callers display them. A top-N chart displays dozens but must see *all*
categories to know which are largest, so `execute_capped` takes an explicit cap and the chart
path uses 100k. Truncation is still reported when even that overflows.

**Dropped series are counted, not summed.** A line chart over more than eight groups keeps eight
and reports `truncatedSeries`. It does not fabricate an "Other" line: adding averages together is
meaningless, and an invented total is worse than an honest count of what is missing.

**A chart's measure filter composes like a card's.** `composed_filter` now reads the binding
filter for bar and line bindings, so global ∧ state ∧ binding holds for charts too and a
workspace filter moves the table and the charts together.

**Two y aggregations is an error, not a silent truncation.** The compiler emits one measure per
line chart. A hand-authored document asking for two is rejected by name rather than charted on
the first — dropping a requested series without saying so is the failure mode this project keeps
refusing.

**The scene cache key includes the binding.** Two charts over one selection with different
dimensions or measures produce different scenes from an identical plan, so keying by plan alone
would serve one chart's buckets to another.

**The Dart hierarchy is sealed.** A painter's `switch` over `ChartScene` is exhaustive, so adding
a fourth kind becomes a compile error at every painter rather than a silently unrendered
component. An unknown `kind` on the wire throws instead of parsing to an empty scene the UI would
draw as "no data".

**Nulls survive the boundary.** A null category label stays null (it is a real group, not `""`);
a null measure stays null (an absent bar, not a zero-height one); a null series y stays null (a
gap, not a plunge to zero). Each is pinned by a test, because any of them defaulting to zero
would draw a wrong chart with no error.

## 3. Every scene answers for what it left out

`ChartScene.partialNotice` is a sentence a user can read, and `isPartial` is the single question
a painter asks before drawing. A truncated category ranking, dropped series, merged buckets and
undated timeline rows all produce one. This is the honest-reporting promise applied to charts:
a painter that draws a partial scene as complete is the same failure as a report sheet that
counts quarantined rows without showing them.

## 5. Limits

Rewritten as tasks land, so this section reads as the current state rather than as 1.4.1's.
What it said then — no painter, no interactions, no goldens — is delivered by §6–§8.

- **One measure per line chart.** The schema allows a list; the engine rejects more than one.
  Multi-measure charts need a legend and axis story that M1.4 has not designed.
- **Multi-series lines now come from the planner** (§11). R3 splits by severity when the data has
  it, so the legend is reachable from a generated document. Without a severity field a line still
  has one series and no legend, which is correct rather than missing.
- **Legend and lane visibility do not survive reopen.** They are view state by decision (§7, §8),
  not persisted selections. Filters and sort do persist, because they change the engine's answer.
- **Goldens cannot check wording.** 54 images pin geometry, colour and layout across three charts,
  two themes and nine states each, but the repo ships no font asset, so the test font draws boxes.
  Text content is asserted behaviourally instead. A bundled font is still owed.
- **Numeric x axes are bucketed like time.** A non-temporal x works, but the ladder is named in
  time units; a numeric axis with a sensible step ladder is not designed.
- **A text time axis gets no chart.** Three corpus files carry a temporal *role* on a `utf8`
  column — CLF month names, RFC3164 with no year, an unresolved day/month order. The query layer
  buckets timestamps and numbers only, so the planner declines rather than emitting a card that
  fails at the first draw (§11). Closing this means parsing those formats in ingest.
- **`layout.hints` stays empty.** Nothing in the runtime reads it and doc 03 §1 defines it as
  where *manual* adjustments persist, which is M1.5. Phone-aware composition is the cap, the
  ordering and the table projection, all of which the renderer does honour (§11).
- **A timeline filtered to one bucket reads as a block.** Geometrically honest — the visible range
  is one bucket — but it does not look like a chart. Keeping context around a selection would need
  a dimming or brushing model M1.4 has not designed.

## 6. Task 1.4.2 — the bar chart, and the golden harness it required

The plan's verification column for this task is "goldens × themes × states", and no golden-image
harness existed. Building it is part of the task, not a follow-up.

| Layer | Where |
|---|---|
| Painter (geometry, cached text, repaint rule) | `lib/runtime/components/bar_chart_painter.dart` |
| Renderer, gestures, semantics, table fallback | `lib/runtime/components/bar_chart_view.dart` |
| Display order in the engine | `morphic-query/src/chart.rs` (`CategoryOrder`) |
| Sort → order mapping | `morphic-core/src/plans.rs` (`category_order`) |
| Declared capability | `morphic-compiler/src/lib.rs` (R5 `interactions.sort`) |
| Behavioural tests | `test/runtime/bar_chart_test.dart` |
| Image tests | `test/runtime/bar_chart_golden_test.dart` |
| Image gate + bootstrap | `.github/workflows/ci.yml` (`Golden image gate`) |

### Decisions

**Horizontal bars.** A phone is narrow and category labels are words. Vertical columns truncate
them into stubs or rotate them, and rotated text is the first thing to fail at 1.3× scale.

**Sorting happens in Rust, and only after the cut.** The toggle persists a `SetComponentSort`;
Dart never reorders a list. `category_scene_ordered` selects the top N *by measure* and then
reorders the survivors, because "the twelve biggest, alphabetically" must still be the twelve
biggest — a label-ordered cut would quietly drop the largest bar. Nulls stay last under every
order. Two engine tests and two widget tests pin exactly this.

**The scene cache had to learn about order.** `plans::for_metric` carries no sort (a chart groups
rather than orders rows), so the fingerprint now includes the order alongside the plan and the
binding. Without it a sort toggle hashed to the same key and was served the previous scene.

**The compiler had to declare the capability.** R5 emitted `sort: false`. Schema pass 5 rejects
state that exceeds declared interactions, so the toggle would have been a *rejected command* —
the painter would have worked and the feature would still have been unreachable. A compiler
test now asserts the capability and that a sorted bar chart still validates.

**The documented top-N ceiling is now actually enforced.** `04-component-registry.md` §2 says
`bar_chart` takes top-N ≤ 50, but `MAX_BAR_LIMIT` was 2000 and the scene clamped to `MAX_GROUPS`
(also 2000) — a document could ask for a chart 96,000 dp tall. Both sides are now 50, declared
twice because neither crate may depend on the other and pinned equal by a test in morphic-core,
the same pattern `MAX_SORT_KEYS` already uses. The compiler still emits at most 12.

**Tap targets and semantics are widgets over the canvas, not painted shapes.** A painted bar is
invisible to a screen reader and to `tester.tap`. Each row is a 48 dp `InkWell` with its own
semantics label, keyed by category.

**The active bar is ringed, not spotlighted by dimming the rest.** Dimming to 45% took a
light-theme bar to 1.75:1 against its surface, under the 3:1 floor for a graphic that carries
meaning. Bar fills are now theme-aware (`accent` on dark, `accentDark` on light; `info`/`infoDark`
for Other), the card is pinned to the token surface, and a test measures all eight colour pairs.

**"View as table" renders the scene, not rows.** It is the chart's own aggregates in another
shape, so it cannot disagree with the bars and puts no row-level work in Dart.

### What the goldens do and do not prove

This repository ships **no font asset** and no `golden_toolkit`. Flutter's default test font
renders every glyph as a box, so these images **cannot verify that the right words are drawn**.
They pin what a text-only test cannot: bar geometry and order, the remainder and null bars,
colour per theme, spacing, the partial-scene notice, and layout at 1.3× text scale. Text
*content* is asserted separately in `bar_chart_test.dart`. Bundling a real font would upgrade
these to full visual checks; that is recorded as a gap rather than implied by the presence of
PNG files.

Nine states × two themes = **18 images**: ready, remainder bucket, null category, one bar active,
label order, partial-scene warning, empty, failed, and 1.3× text scale. The loading state is
deliberately absent — it draws an indeterminate spinner, so its pixels depend on animation phase.

The gate mirrors the Rust `insta` contract: the first run generates the images and the bot pushes
them for review; every later run compares against what is committed. `[regenerate-goldens]` in a
commit message asks for a reviewable regeneration. Both push-back steps now rebase and retry,
because the Rust and Dart jobs can otherwise race on the same branch.

### Evidence

Commit `8d3f650`, run **42492997637**, all six jobs green. Dart: 368 behavioural tests and 18
golden tests. Rust: 627 `#[test]` functions, clippy clean, fmt clean.

The 18 images were generated by that run and pushed by the bot as `8666249`; the run that
carries this paragraph is the first to exercise the *comparison* gate against them, which is
the point of recording it rather than assuming a bootstrap proves the gate.

Five images were inspected directly, not just counted: `dark_ready` (descending bars, fixed
label column, right-aligned values, minimum slivers for tiny values), `light_other` (teal bars
at readable contrast on white, Other distinct in blue), `dark_active` (the outline clearly
visible), `light_text_scale_130` (title wraps to three lines, nothing clipped, values clear of
the bars) and `dark_partial` (the amber warning wraps without pushing content out of the card).

Three rounds were needed. The first failed on one lint (`shouldRepaint`'s parameter must be
named `oldDelegate`), three rustfmt diffs, and a fixture assertion that claimed 5 remainder rows
where the fixture has 4 — the order-independence assertion beside it passed, so only the count
was wrong. The second failed because Flutter's tooling leaves `analysis_options.yaml` modified
in the CI checkout and `git rebase` refuses a dirty tree; the push-back now uses
`rebase.autostash`, verified locally under the same shallow, detached-HEAD, competing-push
conditions before spending another run.

### Still open

- No font asset, so the images are geometry-and-colour checks, not full visual checks.
- Goldens are generated on the Linux CI runner; that runner is the reference platform.
- The bar chart is paintable, `line_chart` and `timeline` are not (1.4.3, 1.4.4).

## 7. Task 1.4.3 — the line chart, two layers, and a frame-time harness

| Layer | Where |
|---|---|
| Base painter (axes, lines) and overlay painter (crosshair, markers) | `lib/runtime/components/line_chart_painter.dart` |
| Renderer, scrub gesture, legend, table fallback | `lib/runtime/components/line_chart_view.dart` |
| Shared value/bucket formatting | `lib/runtime/components/chart_format.dart` |
| Eight-colour series palette | `lib/design_system/tokens.dart` |
| Behavioural tests | `test/runtime/line_chart_test.dart` |
| Image tests | `test/runtime/line_chart_golden_test.dart` |
| Frame-time harness | `test/runtime/line_chart_frame_test.dart` |

### Decisions

**Two painters, not one.** `docs/architecture/07` §3 says tooltips and scrubbing get their own
overlay layer so a pointer move does not repaint the chart. The lines and the crosshair are
therefore separate `CustomPaint`s in separate `RepaintBoundary`s, and the geometry they share is
memoised on scene identity, hidden set and theme. Without that memoisation every pointer move
would hand the base painter a new geometry object and defeat its own `shouldRepaint`.

**The tooltip is a widget, not painted text.** Flutter caches its layout, a screen reader can
read it, and the overlay painter stays free of per-move `TextPainter` allocation. The overlay
paints only the crosshair and the markers.

**A null y is a gap.** The path lifts the pen and resumes at the next defined point. Dropping to
the axis would draw a measurement the engine never made. The test fixture gives `web` no row in
the middle bucket specifically so this is observable, and a golden shows the break.

**Legend visibility is view state, not a command.** Hiding a series changes nothing the engine
computed: the scene still carries every series and point. The schema has no persisted selection
field, so making one would be a schema change for a display preference. It lives in the widget,
like scroll position. The bar chart's sort is the opposite case — it changes which bars Rust
returns, so it is a command.

**Colour follows the engine's index.** Hiding series 0 must not repaint series 1 a different
colour, so the palette is indexed before filtering, not after. A test pins it.

**Eight colours, all measured.** Every entry clears 3:1 against its own theme's card surface;
the bright dark-theme hues fall to ~1.9:1 on white, so the light palette is deeper tones of the
same families. Colour is never the only channel — the legend, the tooltip and the table all name
the series beside its numbers.

**The y axis does not force a zero baseline** unless the data reaches zero. Forcing it on a
series running 990..1000 would flatten the variation the chart exists to show. A flat series is
centred rather than pinned to the bottom edge.

**The table fallback is lazy.** A line scene can hold 2000 buckets; a `Table` would lay out all
of them to show twenty, so the rows are a fixed-extent `ListView.builder`.

### What the frame-time harness proves, and what it only reports

The structural claim is asserted exactly: across a 60-step drag over a **2000-point, 8-series**
chart (the engine's own ceilings), the base painter must report `shouldRepaint == false` every
step and the geometry must stay identical, while the overlay repaints exactly when the bucket
changes. A companion test hides a series and asserts the base layer *does* repaint — otherwise
"zero repaints" would be vacuous.

The wall-clock numbers are **build + layout + paint on the CI test runner**: no GPU rasterisation
and no phone. They are reported as `MORPHIC_FRAME_JSON` and labelled accordingly. **No time
budget is asserted** — a shared runner's timing is not a device budget, and a flaky threshold
would be worse than an honest number. The device budget stays with AT-07's phone harness.

### Evidence

Commit **`d6f2143`**, run **42500967870**, all six jobs green.

- **398 Dart behavioural tests** and **36 golden images**, with the gate reporting
  `bootstrapped: false` — the images were *compared*, not regenerated.
- **627 Rust tests** unchanged; no engine code was needed for this task.
- Frame harness, from the run's own log: `baseLayerRepaints: 0`, `geometryRebuilds: 0`,
  `overlayRepaints: 56` over `scrubSteps: 60` at `points: 2000`. Median 19.79 ms, p95 29.44 ms
  on the host runner. **These are not device frame times.**

Three defects surfaced during verification, and it is worth recording where each came from:

| Defect | Found by |
|---|---|
| A lone reading between gaps drew no pixel at all | **reading the generated golden**, not a test |
| The drag test assumed a scrub begins on pointer-down | CI — Flutter recognises a pan only past touch slop |
| An isolated-point expectation was guessed, not derived | CI — the rule was right, the fixture was wrong |

The first is the argument for the golden gate: no behavioural assertion would have noticed a
value quietly missing from the picture. Two CI defects were fixed alongside it — an empty
`git commit` failing a fully green Rust job, and both golden gates matching the regeneration
marker in commit *bodies*, so a commit merely discussing the marker silently disabled comparison.
The marker is now matched against the subject only.

### Still open

- Same font limitation as 1.4.2: the images pin geometry and colour, not wording.
- The compiler emits `group_by: None`, so real workspaces get a single series and no legend
  until the planner grows that rule in 1.4.5. Multi-series is exercised through the engine
  contract and the fake, not yet through a generated document.
- Legend visibility does not survive reopen; it is view state by the decision above.
- `timeline` is the last unpaintable active type (1.4.4).

## 8. Task 1.4.4 — the timeline, and the end of the placeholder era

| Layer | Where |
|---|---|
| Density/severity painter, severity classification | `lib/runtime/components/timeline_painter.dart` |
| Renderer, tap-to-filter, lane legend, table fallback | `lib/runtime/components/timeline_view.dart` |
| Ten severity tokens | `lib/design_system/tokens.dart` |
| Behavioural tests | `test/runtime/timeline_test.dart` |
| Image tests | `test/runtime/timeline_golden_test.dart` |

**Every type schema v1.0 accepts now has a painter.** `deferredUntil` is empty. The placeholder
widget stays, because the runtime must still label a reserved or unknown type rather than silently
dropping it — and its tests now use a reserved id, which is the stronger claim: the fallback has to
work even for a document that should never have validated.

### Decisions

**Recognised severities get semantic colours.** `ERROR` should look like an error in every
workspace, not take whatever palette slot its frequency earned. Classification is on trimmed,
lower-cased text and never on substrings — a service named `error_handler` is not an error level.
Unrecognised labels fall back to the series palette by lane index, so an arbitrary `groupBy` still
gets distinct colours. All ten severity tokens clear 3:1 on their own surface.

**Segments match lanes by identity, not position.** A bucket with no `ERROR` emits a shorter lane
list; zipping it against the scene's lanes by index would paint that bucket's `INFO` count in
`ERROR`'s red. The fixture deliberately leaves the top severity out of one bucket, and a golden
shows the band in the right colour.

**The count axis uses whole events.** A tick labelled `1.7` names a number of events that cannot
happen. The step rounds up and the axis top sits at or above the tallest column.

**A tap is a half-open range**, `[start, start + step)`, so an event exactly on a boundary belongs
to one bucket. A second tap on a different bucket *replaces* this widget's own previous range
rather than appending — two ranges on one field intersect to nothing — while a time filter the user
set elsewhere is left alone and intersects normally.

**One painter, not two.** 07 §3 asks for an overlay layer so *continuous* gestures do not repaint
the chart. The timeline has no continuous gesture: a tap changes the scene and a legend toggle
changes the visible lanes, so both change what the base layer must draw. A second layer would never
save a repaint. This is recorded in the painter's own doc comment so the deviation is not later
mistaken for an oversight.

**Undated rows are surfaced.** A row whose time is null belongs to no bucket; the scene counts them
and the card says so, rather than quietly understating the data.

### Evidence

Commit **`f8cb419`**, run **42507161800**, all six jobs green, analyzer clean.

- **428 Dart behavioural tests** and **54 golden images**, gate reporting `bootstrapped: false` —
  compared, not regenerated. The 36 pre-existing bar and line images came back byte-identical.
- **627 Rust tests** unchanged; like 1.4.3, this task needed no engine change.
- Two states were read back as images and checked by eye: the stacked lanes in the ready state, and
  the selected state, where tapping a bucket narrowed the workspace, dropped the absent severity
  from the scene, and drew the ring and the breakdown panel.

Only one defect surfaced, an unused import caught by the analyzer; all 428 behavioural tests passed
on the first run.

### Still open

- Same font limitation as 1.4.2–1.4.3: images pin geometry and colour, not wording.
- Lane visibility is view state and does not survive reopen, by the same reasoning as the line
  chart's legend.
- Filtering to one bucket leaves a single column filling the plot. That is geometrically honest —
  the visible range *is* one bucket — but it reads as a block rather than a chart.
- The compiler's R4 emits a timeline only when a severity field is present; `group_by` alone reaches
  lanes through morphic-core's fallback, which the fake mirrors and a test covers.

## 9. Build identity — a tester could not tell one artifact from another

Not a roadmap task. A tester downloaded a current CI artifact and reported that the app still
identified itself as `0.1.0`, reasonably suspecting a stale install. The install was fine; two
things made every build look identical:

- `pubspec.yaml` had been `0.1.0+1` since Phase 0, so every APK carried versionName 0.1.0 and
  **versionCode 1**. Some Android installers treat an equal versionCode as "already installed".
- Settings printed a hardcoded `MORPHIC 0.1.0 · Phase 0 proof of concept`. It never read the
  package version, so no build could change what it said.

A version string that cannot distinguish builds is worse than none, because it looks like an
answer.

**What changed.** CI passes the commit SHA and a UTC build time through `--dart-define`, computed
once outside the retry loop so a retry cannot restamp the same artifact. Settings shows version,
short SHA and build time as *selectable* text, so it can be copied into a bug report. An unstamped
build says `unstamped build` and explains it cannot be matched to a commit — a local `flutter run`
must not look like a CI artifact. The phase label now says Phase 1 · M1.4, and the pubspec is
`0.2.0+2`.

**The stamp is verified, not assumed.** A `--dart-define` that silently failed would restore the
original problem while CI stayed green. The Android job greps the built APK for the commit SHA and
posts the result as a commit comment, so it can be confirmed without downloading the artifact — the
artifact blob host is unreachable from a review sandbox. Run 42520442345 reported
`STAMP_OK: the commit SHA is present in the APK`. A missing stamp fails the job.

Two traps worth recording: `grep -q` exits on first match, which kills `unzip` with SIGPIPE and
fails the pipeline under GitHub's `pipefail` — so the check uses `grep -c`, verified against both
the match and no-match cases before commit. And `unzip -p` with no member streams every entry, so
the check does not care whether the constants landed in the debug kernel blob or an AOT library.

Tests: 7 cases, including one asserting two different commits can never share a label, one reading
`pubspec.yaml` so the displayed version cannot drift from the package, and a widget test proving
Settings renders the stamp rather than a constant — the original defect was in the UI, not the
constant.

## 10. Manual testing on a device, and the first defect it found

The tester installed a CI artifact and worked through the table/paging group: paging bounds,
column sort, per-column filters, "Clear all", and row detail. **All passed**, reported verbally
against build `c43734b`.

That is **informal confirmation, not gate evidence**: no structured artifact, no recorded device
class, no `gitSha` in a machine-readable form. `tools/check_device_evidence.py` would reject it, and
the standing report does not count it toward any acceptance test. It is recorded because it is the
first time a human has driven the shipped app rather than a test harness.

### The defect it found

**Tapping a severity chip on the timeline did nothing.** The painter implements lane toggling and
its widget tests pass from both directions — chips toggle when `select` is declared, and stay a
readable colour key when it is not. But the planner's R4 declared only `filter`, so in every
*generated* workspace the chips rendered disabled. `docs/architecture/04` §2 lists "lane toggle" as
part of the timeline contract, so the feature was documented, implemented, tested, and unreachable.

This is the same class of defect as the bar chart's sort toggle before 1.4.2: **a capability must be
declared end to end.** A renderer test cannot catch it, because the renderer is correct; the fake
bridge in those tests declares whatever the test needs. Only a generated document — or a person
holding the app — exercises the real declaration.

Fixed in `6339c53` by declaring `select: true` in R4, with a compiler test mirroring
`a_bar_chart_allows_the_sort_its_renderer_offers`. Exactly one line of one golden changed.

### What this says about the remaining evidence

Two of the project's gaps look similar from a distance and are not: unit tests prove a renderer
behaves given a spec, and only a device proves the spec the planner actually emits is the one the
renderer needs. The line chart had the same shape of exposure — R3 emitted `group_by: None`, so its
legend was unreachable too — but that one was a missing planner rule, closed by 1.4.5 (§11).

## 11. Task 1.4.5 — planner v1, and the scorecard that found three broken charts

The rule table is complete and the selection claim is measured instead of asserted. Ground truth
is `fixtures/expected/plans.json`: 21 files, 88 expected components, labelled by hand from the file
contents and doc 05 §5 — never from the planner's output. The scorer is
`engine/crates/morphic-core/tests/plan_accuracy.rs`, mirroring the AT-02 one: scorecard written
before any assertion, every miss listed, target read from the JSON, printed in the Rust CI comment.

### The rules as they now stand

| Rule | Fires when | Emits |
|---|---|---|
| R1 | always | `metric_card` "Records" |
| R2 | a numeric measure exists | `metric_card` "Avg ‹field›" |
| **R2b** | **a severity field exists** | **`metric_card` "Errors"** |
| R3 | a bucketable time axis **and** a measure | `line_chart`, split by severity when present |
| R4 | a timestamp axis and no measure | `timeline`, severity lanes |
| R5 | a chartable dimension | `bar_chart`, top-12 + Other |
| R6 | always | `data_table`, ≤8 projected columns |

R3 and R4 remain mutually exclusive. Doc 05 §5 rule 1 reads as though severity alone should force a
timeline; when a measure is present a severity-split line carries strictly more information, so the
line wins. `plans.json` records that disagreement in the `logfmt.log` and `server_logs.log` notes
rather than leaving the two documents silently at odds.

**The error metric's restriction lives in the binding, not in `state`.** State is what the user set
and can clear; clearing it would turn "Errors" into a second "Records" card. Levels are matched on
the exact strings the data uses, because `in` is case-sensitive and logs write `ERROR`, `error` and
`Error` interchangeably. With no error-shaped level present the card still ships and reads zero.

### What the first scorecard found

The first run scored **100% selection — and three charts that could not render.** That is the entire
argument for the render check sitting next to the selection score:

| file | planned | failure |
|---|---|---|
| `access.log` | `line_chart` on `time` | `field 'time' of type utf8 is not numeric` |
| `ambiguous_dates.csv` | `line_chart` on `booked_on` | same |
| `syslog.log` | `timeline` on `time` | same |

A temporal **role** is not a bucketable **axis**. CLF month names, RFC3164 with no year, and an
unresolved day/month order all stay `utf8` on purpose — typing them would invent data. The validator
checks the role, so all five passes were green while the card failed at the first draw. This is the
third instance of the same lesson (§10): a capability has to hold end to end, and the layer that
looks correct in isolation is where the gap hides.

Widening dimension selection exposed a second dead feature. Selection stopped at 12 distinct
values, which is the bar chart's *display* limit; the renderer folds the tail into an "Other"
bucket, so a 20-category column is chartable as 12 bars plus Other. Capping selection there made
Other unreachable from every generated workspace. Selection now follows the role's own ceiling of
50, and a column whose every value is unique is treated as a key instead — from five rows up, the
same floor `morphic-semantic` uses, because two rows with two cities is the sample size talking.

### The score, and what it does not cover

**96.6% (85/88), target 85%. 18/21 exact set matches. 0 charts that do not render.**

The three misses are the text time axes above, and **the labels were not changed to match the fix.**
They still ask for a time view, so the corpus keeps reporting the shortfall until ingest learns
those formats. The scorecard names the gap explicitly. Lowering a label to make a run green is the
same move as lowering a target, and `fixtures/expected/README.md` forbids both.

The three AT-12 guarantees are asserted per file, never averaged: every workspace keeps a table,
every bucketable time axis gets a time view, every severity field gets a restricted error count.
An 85% mean must not be able to excuse a workspace with no table.

**Tuning caveat, same as AT-02:** the rule table was written against this corpus, so 96.6% is an
upper bound on selection quality, not a generalisation estimate. Held-out files are still owed.

### Phone-aware composition

`layout.hints` stays empty deliberately. Nothing in the Flutter runtime reads it, and doc 03 §1
defines it as where *manual* adjustments persist — M1.5's territory. What the adaptive renderer does
honour is the composition, and that is now tested: at most six components, metric cards consecutive
at the front so they flow into one row, the table last, its projection capped at eight columns.
Emitting spans no renderer consumes would have been one more document-only feature.

### Still open

- **Text time axes** get no chart (three corpus files). Needs CLF/RFC3164 parsing in ingest.
- **The cap never binds in practice.** R1–R6 emit at most six, so `cap_components` is tested with
  nine synthetic components rather than by any real profile. It is a guard, not an exercised path.
- **No held-out split.** The score is an upper bound until unlabelled files are scored first.
- **"Why this view?" is now rendered (§12)**, but it is workspace chrome, not a validator pass
  and not a schema component. A document that arrives without an explanation still validates.

## 12. Task 1.4.6 — every component answers for itself

The compiler has attached `reason`, `detail`, `evidence` and `confidence` to every component
since 1.1.3 (doc 03 §1 rule 5, AT-10). Exactly **one** of those four fields was ever drawn:
the metric card's `detail`, clamped to two lines behind a tooltip. The other three crossed the
FFI boundary, passed all five validator passes, and reached nobody. M1.4's exit condition says
"every generated component explains itself"; an explanation nobody can open does not meet it.

### What shipped

`apps/morphic_flutter/lib/runtime/explanation_sheet.dart` is workspace **chrome**, not a schema
component (doc 04 §2 keeps chrome out of v1). One shared `ExplanationButton`, keyed
`explain-<id>`, sits in all five component headers, in the deferred placeholder, and in the
structural document view. The sheet shows:

| Field | How it is shown | Why |
|---|---|---|
| `reason` | a human heading **and** the raw `RULE_TABLE` id | the id is the auditable key; a heading alone would hide which rule fired |
| `detail` | verbatim, unclamped | the metric card's two-line clamp is what this replaces |
| `evidence` | one bullet per string | the profiler's own words, nothing rephrased |
| `confidence` | a percentage plus a bar | with a note that it rates the *field readings*, not whether the chart is useful |

Unknown rule ids fall back to the raw string rather than a guessed heading. Missing evidence
says "No evidence was recorded"; missing or out-of-range confidence says "Not reported" instead
of painting a fabricated 0%. A component with no explanation at all is labelled a **document
defect**, not given a blank sheet or quietly hidden. `rule_label_drift_test.dart` reads
`RULE_TABLE` out of the Rust source, so a new rule cannot reach a user as a bare `R7_something`.

### The gap this found — AT-10 was never fully asserted

AT-10 says "each component has a non-empty explanation with evidence". `Explanation` is
`Option<>` in schema v1.0 and `validate()` deliberately does **not** require it, because v1.0
must still open hand-written and older documents. So the guarantee rested entirely on one
compiler unit test built from one synthetic profile. Nothing checked the corpus. This is the
same shape as 1.4.5's finding: a promise that looked enforced from the layer above.

`plan_accuracy.rs` now asserts, for every component of all 21 fixtures: `reason` is a real
`RULE_TABLE` id, `detail` is non-blank, `evidence` is non-empty with no blank entries, and
`confidence` is in `0..1`. **The schema validator was not tightened** — making `None` invalid
would change a frozen v1.0 contract and break the minimal-document fixture. The compiler is
the component that must always emit, so that is where the gate lives. A hand-written document
without an explanation still validates; the sheet now says so out loud.

### Two contract drifts corrected while wiring it

- **doc 03 §2.1 illustrated `evidence` as `[{field, fact, value}]`.** The shipped type is
  `Vec<String>`. Building a renderer from that example would have crashed on a real document.
  The example, the `reason` and the `detail` are now the actual emitted values. The sheet still
  stringifies a non-string entry, because a saved workspace can predate this build.
- **doc 05 §5 still described the aspirational v1 rule table.** §5.1 now records the three
  deviations: severity + measure yields a severity-split line, not a timeline; a time axis must
  be bucketable; and the "line over row order" in rule 5 was never built. R5's top-12 and R6's
  `layout.hints` are corrected there too.

### A real regression the tests caught

The first run (`58268ca`) was Rust-green and regenerated all 54 goldens, but two degraded-mode
tests failed: adding a 48 dp header button to a **fixed-height** data table left its failure
state 130 dp tall and the engine's error text overflowed the Column by 18 pixels. The test was
right and the layout was wrong. `2705e92` makes that state scroll — a long engine error or a
taller header can no longer clip the evidence a bug report needs. Shrinking the tap target or
relaxing `takeException() == null` would both have been worse fixes.

### Evidence

`58268ca` (code + `[regenerate-goldens]`) → bot `7c36cb0` (54 PNGs) → **`2705e92`, run
42744816936, 6/6 ✅**. Dart `analyze` clean, **447 tests passed**, **54 goldens compared in
LIVE mode** (`bootstrapped: false`), Rust fmt/clippy/test green, **653 Rust tests** (core
66 → 67). The 12 new Dart tests assert wording and reachability from all five renderers; no
golden was added for the sheet, because this repo has no font asset and a PNG cannot prove words.

### Still open

- **The sheet is not a validator pass.** Only generated documents are guaranteed to explain
  themselves; a hand-written one can validate without an explanation. Tightening schema v1.0 is
  a contract change, deferred.
- The four earlier gaps in §11 stand: text time axes, an unexercised cap, no held-out split, and
  `layout.hints` still empty.

## 13. Task 1.4.7 — `ChangeComponentType`, and the last M1.4 row

The registry has always described a compatibility matrix (doc 04 §4), but nothing implemented
it. A person could not switch a bar to a line, a line to a timeline, or any view to the table
without hand-editing the document — and M1.5's AT-13 explicitly expects **type changes** inside
a mixed undo/redo run. 1.4.7 makes the switch a real command, not a UI relabel.

### What shipped

| Layer | Where |
|---|---|
| Closed conversion matrix, pure over `(component, target, profile)` | `engine/crates/morphic-schema/src/type_change.rs` |
| Command arm, atomic validate-all-then-apply | `engine/crates/morphic-core/src/commands.rs` |
| `typeOptions` on snapshot / import / apply payloads | `engine/crates/morphic-core/src/lib.rs` |
| Dart command builder | `lib/engine/interaction.dart` |
| Engine-authoritative menu, table → chart confirmation | `lib/runtime/change_type_button.dart` |
| Header affordance in all five renderers | `lib/runtime/components/*_view.dart` |
| Converted-component heading (not a planner rule) | `lib/runtime/explanation_sheet.dart` |

`morphic_schema::convert_component_type` rewrites **everything** pass 2 and pass 5 care about:
`type`, `binding`, `interactions`, `title`, persisted `state`, and `explanation`. Keeping the
old interactions would make a bar's sort state invalid on a metric card; keeping the old
explanation would claim the planner chose a view a person chose. State that the new view cannot
hold is cleared **and named in the new explanation's evidence**, which 1.4.6's sheet now renders
under the heading "You changed this view". `type_version`, `data_source` and `id` are preserved.

### The matrix is stricter than pass 3 — on purpose

Pass 3 (`validate_bindings`) accepts a `Utf8` column whose *inferred role* is Temporal for a
line's `x` and a timeline's `time_field`. `series_scene` only buckets
`Timestamp`/`Int64`/`Float64`; `timeline_scene` only buckets `Timestamp`. 1.4.5 found three
generated charts that passed all five validation passes and then failed at the first draw. A
manual switch is a second way to build exactly that broken document, so the matrix applies the
**query layer's** rule: a line `x` must be bucketable, a timeline time field must be epoch
milliseconds, and a line → bar switch is refused above 50 distinct x values. The whole
converted document is then checked with `validate()` **and** `validate_bindings()` before it is
committed. A rejected switch in a batch discards the batch's other commands too.

Only the pairs in doc 04 §4.1 are offered. `metric → chart` and `data_table → chart` propose a
default binding from the profile, preferring the columns the old view showed with every tie
broken by field name, so the same file cannot produce two different workspaces after a re-import.
The UI asks for confirmation on `data_table → chart` because that direction invents a binding
rather than carrying one across; the dialog says the raw rows stay one switch back.

### The engine still owns the menu

`component_type_options` returns exactly the targets for which conversion succeeds against the
**live** profile. `Engine::snapshot`, `ImportOutcome` and `ApplyOutcome` carry that map as
`typeOptions`; `EngineController.typeOptionsFor` reads it. No new FFI entry point was added (a
new abstract bridge method would have broken four implementors), and no second compiler lives in
Dart. `API_VERSION` went 6 → **7** because doc 02 §4 says new commands are versioned with the
bridge. Degraded mode has no profile, so it gets an empty map and no button — which also means
the 54 chart goldens did **not** need regenerating: the scripted bridges that render them simply
omit the field and `ChangeTypeButton` occupies zero space.

### Evidence and what remains

The new Rust tests cover the text-axis trap, timestamp-only timelines, high-cardinality x,
state clearing, no-op and unknown targets, every conversion passing all five passes, atomic
batch rejection, persistence across reopen, and the engine-authoritative options map. Dart tests
pin the menu, the confirmation, the command wire shape, error surfacing, and label drift against
`ACTIVE_COMPONENTS` / `TYPE_CHANGE_REASON`. FFI tests prove `changeComponentType` crosses the
JSON boundary and that apply and snapshot agree on `typeOptions`. Exact CI tallies are recorded
in the standing report after the run.

**1.4.7 closes the last M1.4 task row, not the milestone.** All seven tasks are implemented, but
AT-11 is not green, all-five golden coverage is still false (54 PNGs are bar/line/timeline only),
and chart interaction p95 ≤ 33 ms has not been measured on a mid-ARM device. M1.4's exit stays
unmet, exactly as §1–§12 have argued task completion is not exit evidence. The converted
component's explanation debt named in §12 is now paid; undo/redo, layout commands and overrides
remain M1.5 work.
