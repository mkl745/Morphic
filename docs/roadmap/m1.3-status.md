## 1. What 1.3.1 delivers

Execution follows the contract's order exactly: **filter → search → sort → group/agg → page**
(`docs/architecture/05-data-pipeline.md` §4.2).

| Piece | Where | Notes |
|---|---|---|
| Filter tree, 14 operators | `src/filter.rs` | `and/or/not`, six comparisons, `in`, `contains`, `is_null`, `not_null` |
| Compiled filter | `src/filter.rs` | Columns and bounds resolved once, before the scan |
| Stable multi-key sort | `src/sort.rs` | Explicit nulls policy, `f64::total_cmp`, ≤ 8 keys |
| Group-by | `src/group.rs` | Streaming accumulators, 2000-group cap, honest truncation flag |
| Wall-clock budget | `src/budget.rs` | 2 s default, checked every 64k rows and at stage boundaries |
| LRU result cache | `src/cache.rs` | Keyed `(datasetRevision, planHash)`, hit/miss/eviction counters |
| Execution | `src/lib.rs` | `query_page` and `query_groups` share one selection routine |

`query_page` now returns `Result`. An invalid plan is an error, not an empty page, and a grouped
plan sent to `query_page` is rejected rather than answered with ungrouped rows. The one
production caller (`morphic-core`) already returned `Result<_, CoreError>` and now propagates.

### Wire compatibility

`Plan` was extended **additively**. The M1.1 three-field JSON (`{search, offset, limit}`) still
deserializes, and a test pins that, because the bridge and the Dart client still send it. New
fields: `searchFields`, `filter`, `sort`, `groupBy`, `aggs`, `budgetMs`.

The shipped shape stays flat rather than adopting §4.1's nested `search: {…}` / `page: {…}`
form. Changing it would be a breaking FFI revision with no Dart consumer for the new fields
until 1.3.3; that revision belongs with the UI work, not ahead of it.

**`projection` is deliberately absent.** A projected page needs column names in `Page` for the
UI to label it. That is a wire change for 1.3.3. A plan carrying `projection` is rejected by
`deny_unknown_fields` rather than silently ignored.

## 2. Decisions worth recording

These are choices a reader could reasonably have made differently. Each is pinned by a test.

**The filter tree lives in `morphic-query`, not `morphic-schema`.** The DAG rule in
`docs/architecture/01-system-overview.md` §3 is explicit: query may depend on `model` only and
must never know the UI schema. `morphic-model` is restricted to std + serde, so the type cannot
move down there either. `Filter::from_json` therefore reads the same flat wire node the schema
serializes without importing the schema crate, and a test asserts every operator name the
schema documents is accepted — so the two grammars cannot drift silently.

**Nulls are two-valued, not SQL's three.** A comparison against a null cell is false for every
operator, *including* `neq`. A filter chip either matches a row or does not; "unknown" has no
rendering. `is_null` / `not_null` are the explicit way to ask. Consequently `not` complements
the *match*, so `not(eq)` includes null rows. De Morgan still holds, which the property suite
checks over generated trees.

**Bounds coerce into the column's domain.** An `Int64` column compares numerically even when
the bound arrives as `"3"`. An uncoercible bound is a plan error with an actionable message,
never a silent no-match.

**Timestamps compare as canonical UTC text.** Bounds accept UTC milliseconds or ISO-8601 UTC.
`format_utc_ms` is fixed-width, so lexicographic order equals chronological order, and no date
parser has to enter a crate forbidden from depending on ingestion. A date-only bound means
**midnight at the start of that day**; guessing `23:59:59.999` would silently change what an
`lte` chip means.

**Nulls are placed, not compared.** The policy is independent of direction: `nulls: last` means
last ascending *and* descending. Flipping nulls with the direction is a common surprise, and a
chip that says "nulls last" must mean it.

**The filter is compiled before the scan.** Resolving column names and coercing bounds per row
would charge millions of string comparisons and allocations to a query whose target is 150 ms.

**Group keys are `Vec<String>`, not a joined string.** Any separator eventually appears inside a
value and silently merges two groups. Output order is first appearance, so a sorted input
yields sorted groups deterministically without a second sort.

**The group cap counts what it drops.** Beyond 2000 groups the engine stops accumulating but
keeps counting, so `totalGroups` and `truncated` tell the truth instead of presenting the first
2000 groups as the whole answer.

**Both paths share `full_selection`.** A grouped answer cannot disagree with the table it
summarizes — the groundwork for 1.3.5's no-torn-state requirement.

## 3. Honest limits

- **The budget cannot interrupt a sort.** Rust's `sort_by` is opaque, so checks sit at row
  checkpoints in the scan and the group pass, and at stage boundaries. Selection is what scales
  with hostile input and it is checked; an already-selected vector's sort is not interruptible.
- **Search is still a linear scan.** Field-scoped, case-insensitive, correct — but not indexed.
  No index is claimed.
- ~~The cache is a container, not yet wired.~~ **Resolved in 1.3.2:** `component_page` and
  `metric_data` both go through it, keyed by `(dataRevision, planHash)`.
- **`distinct_count` holds a set per group.** Bounded by the group cap, not by a cardinality
  estimate. A high-cardinality field across 2000 groups is the worst case.
- **LRU recency is O(capacity).** Deliberate at capacity 32; the doc says to replace the
  structure rather than raise the constant.

## 4. Evidence

### Tests

**540 Rust tests** workspace-wide (up from 511), of which `morphic-query` now has **50**: 21
original, 23 new example tests, 1 measurement test, 5 property tests.

The property suite (`tests/properties.rs`) is what the plan asked 1.3.1 for. Seeded and
deterministic, with `MORPHIC_PROP_CASES` / `MORPHIC_PROP_SEED` overrides matching the fuzz
smoke's convention. Over 300 generated tables and filter trees it checks:

- double negation; idempotence and commutativity of `and`/`or`
- De Morgan in both directions
- `and` = set intersection, `or` = set union, absorption
- filter and search intersect rather than override
- sort is a permutation, is ordered, places nulls by policy, keeps ties in source order, and is
  idempotent
- pages tile the matching rows exactly once and the total never drifts
- group counts partition the selection

### Performance — measured, and what it does not prove

`tests/perf.rs` builds a deterministic 100k × 10 table and writes `target/query-perf.md`, which
CI prints in the Rust report.

| Workload | Run A | Run B | Run C | Matched |
|---|---|---|---|---|
| filter (`in` + `gte`) + 2-key sort + page | **70.3 ms** | **36.3 ms** | **55.0 ms** | 33,706 rows |
| same filter + sort + group/agg | 83.3 ms | 43.7 ms | 65.9 ms | 2 groups |
| unfiltered first page (baseline) | 2.0 ms | 1.3 ms | 2.0 ms | 100,000 rows |

The spread across three runs of essentially identical code is itself the argument for not
treating a CI number as a benchmark: the same query took 36 ms, 55 ms and 70 ms on different
shared runners. Run C (`976578a`, 42335467607) is the final all-green one.

**This does not confirm the exit criterion.** AT-07 and the M1.3 exit demand ≤ 150 ms on a
**mid-class ARM device**; the plan marks it **(H)**, a hypothesis. A CI x86 runner is not that
device. 36–70 ms here is encouraging and says the algorithm is not accidentally quadratic — it is
not the device number. The assertion in the test is a deliberately loose 5 s regression ceiling,
because a shared runner is not a benchmark machine.

Two of the first draft's hand-computed test expectations were wrong (descending order was
reversing ties, and the leading group after a sort was the null group, not `eu`). Both were
caught by modelling the semantics independently before pushing, not by CI.

## 4b. Task 1.3.2 — the command layer

`SetGlobalFilter`, `SetComponentFilter`, `SetComponentSort`, `SetSearch`, applied as atomic
batches, with the result cache finally in the request path.

| Piece | Where |
|---|---|
| `ComponentState` (filter, sort, search) on `ComponentSpec` | `morphic-schema/src/lib.rs` |
| Pass-4 filter ceilings, pass-5 state/capability checks | `morphic-schema/src/lib.rs` |
| Command vocabulary + atomic application | `morphic-core/src/commands.rs` |
| Plan composition (global ∧ component ∧ binding) | `morphic-core/src/plans.rs` |
| `apply`, `component_page`, `compute_count`, cached `metric_data` | `morphic-core/src/lib.rs` |
| Selection-aware aggregation | `morphic-query` (`aggregate_over`, `select_rows`) |

### Decisions

**`state` was already in the contract.** `docs/architecture/03` §2.1 specifies a per-component
`state` object; nothing implemented it. It is `skip_serializing_if` empty, so a generated
document stays byte-identical to a pre-M1.3 one and a document written before it still decodes.
The published JSON Schema change is purely additive.

**`SetGlobalFilter` replaces the whole set.** Add/edit/remove-a-chip is composed by the UI and
sent as the resulting set. "Clear all" is an empty vector, and there is no remove-by-index
command whose index could go stale between the tap and the apply.

**Atomic means nothing was applied, not something was rolled back.** Commands transform a
clone; the result is validated as a whole; only then is it saved and swapped in. A test rejects
the second command of a two-command batch and then reopens with a *fresh engine* to prove the
first one never reached the disk.

**A no-op is free.** Setting a value that is already set does not bump the revision, touch
`modified_at`, save, or name an affected component. That is what makes a debounced search field
cheap and a repeated tap idempotent.

**The cache key is `(dataRevision, planHash)`, not the document revision.** Editing one
component bumps the document but leaves every other component's plan byte-identical, so those
hit the cache. Keying by document revision would invalidate everything on every keystroke and
make "affected-component recomputation only" impossible. `compute_count` exposes actual
executions so the claim is asserted, not asserted-by-comment.

**Filters compose as global ∧ component ∧ binding, binding last.** A metric card's binding
filter is part of what the card *means*; putting it last means a user filter can narrow the
card but never widen it.

**Field references are checked at command time.** A typo becomes an error the user sees, not a
chip that silently matches nothing. In degraded mode (source unavailable) the check is skipped
rather than making the workspace unusable offline.

**The session lock is held across the save.** That serializes edits against reads. For a
single-user local app a torn read is worse than a brief wait; debounce and autosave belong to
the UI layer.

### Two defects this fixed

Both made the feature unusable rather than merely slower:

1. **`metric_data` parsed its binding's filter and then ignored it.** A card declared as
   `count where level = ERROR` counted every row. Now applied, with a regression test.
2. **The compiler emitted metric cards with all interactions off**, contradicting the
   contract's own example (`"filter": true`) and blocking AT-06's tap-to-filter. They now allow
   filtering, still not sort or search. This moved 19 lines across the compiler goldens; the
   bot's diff was reviewed and contained nothing else.

### The bug the tests caught

The metric cache was first keyed on `plan.hash()` alone. Two unfiltered cards over the same
selection have **identical plans**, so the average card was served the record count from cache.
Two pre-existing tests failed immediately (core's `metric_data_resolves_the_binding_in_rust`
and the bridge's `metric_data_computes_in_rust`). The key now hashes the plan together with the
aggregation op and field, and `two_cards_over_the_same_selection_do_not_share_a_cache_entry`
pins it.

A third failure was the test being wrong, not the engine: a fixture row with a null measure was
expected to sort first under `desc`, but nulls-last correctly placed it last.

### Limits

## 4c. Task 1.3.3 — the table becomes interactive

Sort, per-column filters, search and row inspection, driven by the 1.3.2 command layer. This is
the task where "no Dart-side data logic" stops being trivially true and becomes a constraint
that shaped the design.

| Piece | Where |
|---|---|
| `morphic_apply_commands`, `morphic_component_page` (API 4 → 5) | `apps/morphic_flutter/rust/src/lib.rs` |
| Command/filter vocabulary, sort cycling, operator sets, coercion | `lib/engine/interaction.dart` |
| `applyCommands`, `componentPage` | `lib/engine/{bridge,engine_controller}.dart` |
| Capability gates, persisted state, dtype and top-value lookup | `lib/runtime/component_registry.dart` |
| Sort headers, filter buttons, chips, debounced search | `lib/runtime/components/data_table_view.dart` |
| Type-aware filter menu | `lib/runtime/components/table_filter_menu.dart` |
| Whole-record bottom sheet | `lib/runtime/components/row_detail_sheet.dart` |

### The decision that mattered

**The table stopped sending query plans.** It previously called `query_page` with a plan it
assembled itself. Keeping that and adding sort/filter fields to the plan was the obvious small
change, and it was wrong: the composed plan is **global ∧ component ∧ binding**, and a plan
built in Dart would silently omit the global filters that 1.3.4 adds. The table now sends
commands and asks for `component_page(id)`, so Rust is the only place a plan is ever built.

The Dart side is left with exactly two jobs: compose commands, render what comes back. There is
no `sort`, `where` or substring match over rows anywhere in `lib/` — the only row-level code is
a test double, and its docstring says the authoritative semantics live in `morphic-query`.

### Decisions

**One sort key at a time.** The engine allows eight. A phone header has room for one indicator,
and a shift-tap is not a phone gesture. Tapping a second column replaces the key. Multi-key is a
documented limit, not an accident.

**The indicator is read from the document, never held in the widget.** `ComponentInteraction`
is parsed from `spec['state']` on every build. A rejected command therefore cannot leave the
header claiming a sort the engine refused, and a reopen shows the same arrow (AT-07). The FFI
test proves it end to end: apply, close, reopen, and the first page is still ordered.

**The menu offers only operators the column can mean.** A number gets comparisons and never
`contains`; a boolean gets *is* and the null tests; a timestamp gets date bounds with a picker;
text gets contains/equals/one-of with the engine's own frequent values as suggestions. Every
type can ask *is empty* / *is not empty*, which need no value. An unrecognised dtype falls back
to text rather than to an empty menu, so degraded mode stays usable.

**Bounds are typed before they are sent.** `20` on an integer column is the JSON number 20, not
the string `"20"`; one-of sends an array because that is what `Filter::from_json` reads;
unparseable text disables Apply instead of sending a bound the engine will reject.

**One gesture, one destination.** A cell tap used to open a single-cell dialog. It now opens the
whole record in a bottom sheet — a wide table scrolls horizontally, so the rest of the row was
the part you could not read. Nulls say "No value (null)" rather than rendering blank.

**Clear-all is one batch.** Filter and search clear together, so the table cannot flash a
half-cleared state between two revisions.

### The bug the tests caught

The boolean menu **displayed "True" while its bound was the empty string**. `coerceBound` returns
null for empty text, so Apply was disabled and the sheet looked broken with no explanation. A
choices widget that shows an option must hold that option; the bound now starts at `true`. The
widget test found this on the first run — it tapped Apply and no command was sent.

A second defect was found by reading, not by a test: `didUpdateWidget` compared
`old.ctx.engine.revision` with `widget.ctx.engine.revision`. Both contexts hold the **same**
controller, so both sides always read the new value and the branch could never fire. The last
rendered revision is now remembered in the State object.
`a command applied elsewhere refreshes this table` is the regression test — without the fix the
table would have ignored the global filter bar entirely in 1.3.4.

### Evidence

**583 Rust tests** (572 → 583; bridge 32 → 43) and **267 Dart tests** (188 → 267: 46 vocabulary
unit tests, 26 interaction widget tests, 7 controller contract tests). `flutter analyze`: no
issues. Verified on `97d20cb`, run **42380094459**.

The plan's stated verification for this task is widget tests, and they assert the *contract*
rather than the pixels: every interaction test inspects the recorded command batch, and several
also assert `bridge.plans` is empty — the table must not have built a plan at all.

Three drift gates read the Rust source directly, so the vocabularies cannot drift silently:
the `Command` enum's variants against the tags Dart emits, `FILTER_OPS` against every operator
the menu offers, and `DataType::as_str()` against the dtypes the menu understands.

### Limits

- **AT-06 is still partial.** Chips exist and are removable per component, but the *global*
  filter bar and tap-to-filter from a chart or card are 1.3.4; one-revision consistency across
  components is 1.3.5.
- **AT-07's latency half is unmeasured.** The indicator and scroll reset are tested; "feels
  instant on a mid-class phone" is not, and the 100k×10 ≤ 150 ms budget is still only evidenced
  on CI x86.
- **No projection**, so a table binding's `columns` list is still not honoured by the engine.
- **The timestamp menu writes a date, not an instant.** `YYYY-MM-DD` means midnight UTC at the
  start of that day; the field says so. Time-of-day bounds and local zones are not offered.
- **Search is per-component.** A single search box that filters everything is N commands in one
  batch, which is 1.3.4's global bar, not a special engine path.

## 4d. Task 1.3.4 — the workspace filter bar and tap-to-filter

A filter that narrows *everything*, and metric cards that become controls.

| Piece | Where |
|---|---|
| Chip bar: add, edit, remove, clear-all | `lib/runtime/global_filter_bar.dart` |
| `globalFilters`, `fieldNames`, `dtypeOf`, `topValuesOf` | `lib/engine/engine_controller.dart` |
| Filter-set algebra (canonical key, toggle, edit-in-place) | `lib/engine/interaction.dart` |
| Optional field picker on the 1.3.3 menu | `lib/runtime/components/table_filter_menu.dart` |
| Tap-to-toggle, applied state, revision tracking | `lib/runtime/components/metric_card_view.dart` |
| Bar mounted above the layout | `lib/runtime/workspace_view.dart` |

### Decisions

**Every mutation is the same command.** Add, edit, remove and clear-all all send
`SetGlobalFilter` with the whole resulting set. There is deliberately no remove-by-index
command: an index can go stale between the tap and the apply, and 1.3.2 had already chosen
whole-set replacement for exactly that reason. The bar is therefore a renderer of
`engine.globalFilters` plus four ways to produce the next list.

**Presence is structural, not identity.** A card's binding filter and the chip the engine echoed
back are different map objects with the same meaning. `filterKey` canonicalises a node (sorted
keys, recursive) so a card shows as applied when the *same predicate* arrived from the bar, and
tapping it removes rather than duplicating it.

**A card with no predicate of its own opens the menu.** The plan says "metric-card tap → toggle
its filter", and the compiler currently emits only `count` and `avg` cards — neither has a
binding filter, so the literal reading would ship a control no generated workspace can reach.
A filterable card therefore toggles its own predicate when it has one, and otherwise opens the
workspace filter menu. The affordance text says which of the two will happen.

**One sheet, two scopes.** The 1.3.3 column menu gained an optional field picker rather than a
second menu being written. Choosing a field re-derives the type, the operator list and the
frequent values; an operator the new type cannot mean falls back to the first rather than
leaving a dropdown value that is not in its items.

**The bar scrolls with the content.** A pinned bar plus a sticky table header leaves very little
room for rows on a phone. It is the first block in the layout, above every component, because
what it sets applies to every component.

### The bug this found

**A failing read notified listeners during the build phase.** The bridge call is synchronous and
an `async` function runs straight through to its first `await`, so when `metric()` failed it
called `notifyListeners()` inside the card's `initState` — marking the ancestor `AnimatedBuilder`
dirty while the framework was still building:

```
setState() or markNeedsBuild() called during build.
#5 EngineController.metric (engine_controller.dart:292)
#6 _MetricCardViewState._fetch (metric_card_view.dart:111)
#7 _MetricCardViewState.initState (metric_card_view.dart:48)
```

This was not a test artifact. Any workspace whose metric could not be computed — degraded mode,
a missing source file, an unknown component — would have crashed on a device. The read paths
(`metric`, `componentPage`, `page`) now yield once before touching the bridge, so the failure is
still reported but lands after the frame that triggered it.

The same latent defect as 1.3.3 was also fixed in `MetricCardView`: it compared
`old.ctx.engine.revision` with `widget.ctx.engine.revision`, which is the same controller on both
sides. Without remembering the last rendered revision, a global filter change would have left
every card showing a stale number — the exact torn state 1.3.5 exists to rule out.

### Evidence

**586 Rust tests** (583 → 586) and **301 Dart tests** (267 → 301: 12 filter-set unit tests,
20 widget tests, 2 controller contract tests). `flutter analyze`: no issues. Verified on
`44221b1`, run **42388218245**.

AT-06's two hard clauses are now asserted rather than described:

- *all bound components reflect the intersection within one engine revision* — one FFI test
  applies a single global filter and checks the record count, the average and the table's total
  row count afterwards, and that all three were named affected.
- *clearing restores exact prior aggregates* — the same test captures the values before, filters,
  clears, and compares against the captured values rather than against a fresh expectation.

The widget suite hosts the **production route** (`WorkspaceView` inside an `AnimatedBuilder`),
not a bespoke column. The first round used a custom host and 12 of 13 failures were artifacts of
a layout the app never renders; testing the real route removed the variable.

### Limits

- **AT-06 still needs 1.3.5.** The intersection and the chips are proven per command; what is not

- **The compiler still emits no filtered cards**, so tap-to-toggle is exercised by tests and by
  hand-authored documents. Generating a card *about* a subset (error counts, null counts) is
  planner work in M1.4.
- **Device latency is still unmeasured**, for filtering as for sorting.

## 4e. Task 1.3.5 — no component may paint a superseded selection

The last task in M1.3, and the only one whose deliverable is a *negative*: that a frame never
shows two components on two different selections.

| Piece | Where |
|---|---|
| Settled-page-only range label | `lib/runtime/components/data_table_view.dart` |
| Revision captured before the read, checked before adopting | both component readers |

### The tear was already visible, in text

**The table footer stated a range from the previous page while the next selection was loading.**
`_footer` read `_page` regardless of load state, so a filter change printed `1–2 of 4` directly
beside a metric card that already read `2`. Not a subtle race — the one widget whose job is to say
how many rows match was asserting a number for a selection the workspace had left. Only a settled
page may state a range now. An empty label is honest, and the header spinner says why.

### Why `_attempt` was not enough

Both readers already discarded a response superseded by a newer fetch **of the same component**.
That is a different question from *which revision is this response about*. A read could be
computed at revision N, the document could move to N+1, and the response would still be adopted
because no newer fetch of that component had started.

Each reader now captures the revision before its await and refuses a response whose revision the
document has left, re-reading instead. In today's wiring a revision change also triggers a
refetch, which usually masks the problem — the guard is what makes consistency **true rather than
timely**, and it is what will still hold when the bridge moves off the UI isolate.

The check is deliberately conservative: the revision is captured by the reader, not reported by
the engine, because `component_page` returns `morphic_query::Page`, which carries no revision
(`metric_data` does). A read that happens to be served at a newer revision than the reader
expected is therefore discarded and repeated rather than trusted. That costs an occasional extra
read and never shows stale data. Making it exact means adding a revision to the page envelope —
an additive FFI change, deliberately left out of an S-sized task.

### How it is tested

The integration tests drive a controller that **computes each read eagerly and delivers it later**,
on a gate. That is the only way to observe a response from a revision the workspace has already
left, and it is exactly the shape the bridge will take once reads move off the UI isolate. Six
tests:

- every read following one command carries the same revision, and both bound components are read;
- a slow component shows a loading state, never the previous selection's range, while a fast one
  has already updated;
- a response computed for a superseded revision is discarded and re-read, with the readers hosted
  on a pinned context so no rebuild-driven refetch can mask the guard;
- the same guard protects a metric value;
- two commands whose responses are released **out of order** converge on the last revision;
- clearing restores every component, and the card does not keep the filtered count while the
  table is already restored.

Two FFI tests express the same invariant at the engine boundary: a batch spanning a global and a
component filter is observed whole (the table sees both, the card sees the global one, and the
card reports the batch's revision), and a rejected batch leaves *every* component on the previous
revision with `globalFilters` still empty.
